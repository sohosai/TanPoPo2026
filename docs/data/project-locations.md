# 企画の実施場所データ

企画ごとの実施場所（建物・部屋、屋外ブース、ステージ）と実施日は、次の2つから決まる。

| 対象 | 情報源 | 反映先 |
| --- | --- | --- |
| 屋内・屋外の企画 | 雙峰祭実行委員会の「企画実施場所一覧」（屋内・屋外の xlsx） | `apps/api/data/sources/project-locations.json` |
| ステージ企画 | SOS 公開 API のカスタム項目 `ステージ実施場所 確定` | `apps/api/data/sources/stage-projects.json` |

どちらにも無い企画は場所が空になり、画面では「未定」と表示される。`bun run check:map-data` は、場所が空の企画を警告として一覧に出す（エラーにはしない）。

## project-locations.json

キーは企画番号、値はその企画の実施場所の配列。

```jsonc
{
  "56":  [{ "placeId": "bldg-6a", "room": "401（書実習室）", "days": ["Day1", "Day2"] }, ...],
  "60":  [{ "placeId": "booth-c", "room": "C4", "days": ["Day2"] }],
  "158": [{ "placeId": "bldg-library", "room": "集会室", "days": ["Day1", "Day2"] }]
}
```

- `placeId` は `apps/api/trpc/routers/place.ts` の `Place.id`。
- `room` は場所の中での位置。建物では部屋番号（備考に部屋名があれば括弧で添える）か部屋名、屋外ではブース番号。
- `days` はその場所で実施する日（`前夜祭` / `Day1` / `Day2`）。企画の実施日（`Project.schedule`）は全場所の `days` の和になる。

画面での表示は、部屋番号なら続けて（`1B208`）、部屋名なら空白を挟む（`6A エントランスホール`）。屋外ブースは場所名だけ（`石の広場周辺`）。

## 取り込み

一覧が更新されたら、xlsx を指定してスクリプトを実行し、生成された JSON をコミットする。

```sh
bun run import:project-locations <屋内_企画実施場所一覧.xlsx> <屋外_企画実施場所一覧.xlsx>
bun run check:map-data
```

スクリプト（`scripts/import-project-locations.ts`）の変換規則:

- 企画番号の無い行（委員会企画）は取り込まない。
- 場所 `1B208` → `bldg-1b` の部屋 `208`。`6A` のように建物名だけなら備考を部屋名にする。
- 場所 `C4` のような屋外ブースは、英字ごとのテント列 `booth-c` に紐付け、`C4` を `room` に持つ。
- `中央図書館` `開学記念館` `セキショウフィールド` は個別の Place に対応させる。
- 実施日は月日だけで判定する（`10/30` → 前夜祭、`10/31` → Day1、`11/x` → Day2）。表記の揺れや曜日の誤記に影響されないようにするため。
- 解釈できない場所・実施日があればエラーで止まる。新しい建物や屋外エリアが出てきたら、`place.ts` に Place を足し、必要ならスクリプトの対応表を更新する。

## stage-projects.json

キーは企画番号、値は実施ステージの `placeId`。

```jsonc
{ "5": "stage-1a", "14": "stage-united", "87": "stage-kaikan-kodo" }
```

SOS のカスタム項目の略称を次のように対応させる。

| 略称 | placeId |
| --- | --- |
| `1A` | `stage-1a` |
| `UNI` | `stage-united` |
| `会館（講堂）` | `stage-kaikan-kodo` |
| `会館（ホール）` | `stage-kaikan-hall` |

SOS の登録内容が変わったら、スクリプトを実行して生成された JSON をコミットする。取得先は環境変数 `SOS_API_URL`（既定は本番の SOS）。ステージ企画なのに実施ステージが無い・想定外の略称がある場合はエラーで止まる。

```sh
bun run import:stage-projects
```

グランプリ投票のステージ部門は、この実施ステージでステージ企画を分ける（会館の講堂とホールは1つの「会館ステージ」）。ステージ企画は一般部門には投票できない。

## 屋外のテント列

屋外ブースは、配置図の記号の英字ごとに1つの Place（`kind: 'outdoor'`、id `booth-<英字>`）で表し、個々のブースは `room`（ブース番号）と座標で表す。

ブース番号は配置のための内部的な番号で、画面には出さない（屋外ブースの場所は `石の広場周辺` のように場所名だけを表示する）。

ブースごとのテントの形は `apps/web/app/components/features/Map/data/booths.geojson`（`properties.booth` がブース番号の Polygon）にある。建物のポリゴンと同じく地図のジオメトリとして web 側だけが持ち、テントの中心は web 側でこの形から求める（`apps/web/app/components/features/Map/booths.ts`）。テント列の Place の代表点（`place.ts` の `OUTDOOR_ROWS`）は、その列のテントの中心。

テントの形と座標は、屋外配置図（PDF）から次の手順で求めた。

1. PDF の各ページから、テント（水色）・軒下（ピンク）の塗りの図形と、ブース記号（`C4` など）の文字の位置を取り出す（ページ左の一覧表にある記号は除く）。
2. ページごとに、建物の角など配置図と OSM の建物ポリゴンの両方で特定できる点を 3〜6 個対応させ、配置図の座標 → 経緯度の相似変換（拡大縮小・回転・平行移動）を最小二乗で求める。対応点での誤差は 0.1〜1.9m。
3. 1つの図形に複数のブース記号が入っている（6脚テントや軒下の並び）ときは、図形の外接長方形を長辺方向に記号の数で等分し、記号の並び順に割り当てる。図形が重ねて描かれている（P3・P4 の 6脚テントの右半分に 4脚テントの図形が重なっているなど）ときも、外側の図形を等分した形を使い、テントどうしが重ならないようにする。
4. 各ブースの長方形を経緯度に変換する。

配置図にある案内所（6脚大テントの画像）とゴミ箱（黄緑の図形）の位置も同じ変換で経緯度にし、`place.ts` の `kind: 'information'` / `'trash'` の場所に持つ。案内所のテントは、配置図の画像が実寸でないため、画像の中心と向きに実寸 5.4m × 3.6m の長方形を置き、`apps/web/app/components/features/Map/data/information.geojson` に持つ。

配置図が変わったら同じ手順で作り直す。`bun run check:map-data` は、屋外ブースの企画に座標が無いとき、案内所にテントが無いときにエラーにする。

軒下（E・J・N・Q・R 列など）のように建物に重なるテントは、配置図どおりの位置のまま持ち、3D 表示で建物側を半透明にして見せる（[地図上の会場情報](../web/map-layers.md) の 3D 表示）。
